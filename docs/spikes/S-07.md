# S-07 · IPC throughput — findings

**Outcome: A9 confirmed.** NDJSON over a Unix domain socket, decoded with `Codable` in Swift, carries 50,000 session-shaped events at 25,000 events/s in order with none dropped, with p99 write-to-decoded latency around 0.1 ms — about 50× under the 5 ms budget in §9. The fallback (coalescing events per display frame in the engine) is not needed for the transport, and D-04 stands unchanged.

## What was built

`spikes/s-07-ipc/` (throwaway):

- `server.mjs` — Node 22 server on a Unix socket. After a `spike.start` request it streams `session.event` JSON-RPC notifications (one `socket.write` per event, as the engine would), then `spike.done`. Events carry `seq`, an ISO `ts`, a `type`, a typed `data` payload, and `sentNs` from `process.hrtime.bigint()` taken just before the write. Mix: 88% `assistant.delta` (~250 B line), 10% `assistant.usage`, 2% `tool.completed` with a 1.8 KB output.
- `client/` — SwiftPM executable (Swift 6 mode, release build). Reads the socket with `read(2)` into a 64 KB buffer, splits on `\n`, decodes each line with `JSONDecoder` into a `Notification` enum whose `SessionEvent` switches on `type` into typed payloads, then reads `CLOCK_UPTIME_RAW`. Latency = decoded time − `sentNs`.
- `run.sh order|latency|report` — builds the client, starts the server, runs and asserts. `order` asserts one paced run; `latency` takes the median p99 of three paced runs (see below).

**Clock.** Node's `process.hrtime` and `clock_gettime_nsec_np(CLOCK_UPTIME_RAW)` both read `mach_absolute_time` on macOS, so both processes share one monotonic clock. The start handshake measures the offset (server clock − client round-trip midpoint); it is always within half the handshake round trip (|offset| ≈ 15–100 µs against a 150–830 µs round trip), which confirms the shared base. The `latency` check asserts |offset| < 1 ms.

## Measurements

Apple M2 Pro, macOS 27.2.1, Node 22.17.0, Swift 6.4.2, release build of the client, nothing else heavy running. 50,000 events per run.

Paced at 25,000 events/s (10 consecutive runs):

| | min across runs | max across runs |
|---|---|---|
| Received rate | 25,000 /s | 25,018 /s |
| p50 | 0.011 ms | 0.013 ms |
| p99 | 0.045 ms | 0.135 ms |
| p99.9 | 0.114 ms | 0.635 ms |
| max | 0.30 ms | 1.25 ms |

Every run: 50,000 received, in `seq` order, 0 gaps, 0 out of order.

One earlier run showed a p99.9 of 8.9 ms and a max of 10.7 ms with p99 still 0.99 ms — a scheduling stall on a loaded desktop. p99 has margin for that; the tail above p99.9 is not a budget metric.

Unpaced burst (server writes as fast as the socket drains, 3 runs): 187,000–190,000 events/s received, p50 0.65 ms, p99 1.09–1.10 ms, max 1.27–1.47 ms. Latency here is mostly queueing in the socket buffer, and still under budget at roughly 9× the required rate.

### Under CPU contention

While three other sessions were building on the same machine (load average ~5.5), most runs stayed at p99 0.03–0.6 ms, but about one run in six had p99 7.6–9.6 ms with a max of 15–19 ms. Throughput and ordering were unaffected (every run ≥ 24,970 events/s, 0 gaps).

To reproduce that deliberately, ten `yes > /dev/null` processes saturated all 10 cores (6 P + 4 E) and 4 runs each were taken at default QoS and with the client thread at `QOS_CLASS_USER_INTERACTIVE`:

| | p50 | p99 | p99.9 | max |
|---|---|---|---|---|
| default QoS | 0.05–0.12 ms | 1.3–9.2 ms | 2.7–25 ms | 4.3–30 ms |
| user-interactive QoS | 0.05–0.15 ms | 1.6–10.7 ms | 6.8–23 ms | 7.3–27 ms |

Raising the reader's QoS did not help. The stalls are the reader (or the kernel handoff) being descheduled for 10–30 ms while events keep arriving; at 25,000 events/s one 15 ms stall alone delays ~375 events, which is most of a 1% tail. Note that the spike's pacer is a `setImmediate` busy loop that holds a full core itself, so it adds to contention more than the real engine would.

Engine-side coalescing would not fix this: the delay is in getting the reader scheduled, and batching only adds latency on top. That is why the `latency` check takes the **median p99 of three runs**: a single run measures the scheduler on whatever else the machine is doing, not the transport. H-07 should pin the reference runner's load when it turns §9 into a gate.

## Conclusion and notes for later units

- **A9: confirmed.** No engine-side coalescing is needed to meet "event delivery p99 < 5 ms" at the transport and decode layer. D-04 is unchanged; no new decision. On a fully saturated machine the tail can exceed 5 ms, but that comes from scheduling, and the fallback would not fix it.
- The measurement stops at the decoded value. Getting from there to the view is A-02/A-05's share of the budget: at 25,000 events/s, a main-actor hop and an `@Observable` mutation per event would be the likely cost, so batching store updates per run-loop turn (not per event) belongs in the app, not the engine.
- p50 of ~11 µs bounds the per-line `JSONDecoder` cost plus socket transit. `ts` was decoded as `String`; with this toolchain (Swift 6.4.2) `.iso8601` does accept the millisecond timestamps `Date.toISOString()` emits, so E-02 can decode it as `Date`, but date parsing was not included in these numbers.
- `sentNs` was sent as a string because uptime nanoseconds exceed 2^53 after ~104 days; the real protocol should avoid nanosecond integers in JSON numbers for the same reason.

## Reproduce

```sh
make verify UNIT=S-07
spikes/s-07-ipc/run.sh report   # paced and unpaced summaries as JSON
```

The spike is not part of the default `make verify`: it depends on scheduler timing on the machine running it.

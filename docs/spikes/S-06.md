# S-06 · MCP connectivity — findings

**Outcome: partial. A8 is confirmed for GitHub only.** Through the pinned SDK (`@github/copilot-sdk` 1.0.28), GitHub connects and lists its 46 tools, which cost **13,835 tokens** of tool definitions according to `contextInfo`. No prompt is needed. Datadog and ClickUp reach the runtime's own OAuth flow (RFC 9728 discovery, dynamic client registration, PKCE, loopback redirect) and stop at the consent page, which only the owner can approve. Snowflake was not tried, because its endpoint is specific to an account, an admin has to create it, and Q-06 is unanswered. The runtime can own OAuth from start to finish, and it can also take tokens from the host. So the A8 fallback ("host-managed tokens supplied by Pica") is available as well, not only needed as a replacement. A8 stays open until the three servers that need the owner connect.

All runs are from 2026-11-14 on Copilot Free (S-01). Each server got its own session, so one blocked server did not stop the others. Results, redacted, are in [`S-06-results.json`](S-06-results.json).

## What was built

`spikes/s-06-mcp/s06.mjs` (throwaway). Like S-01, it imports the SDK from the adapter's own `node_modules`.

For each server it creates a session whose only `mcpServers` entry is that server. It calls `session.rpc.tools.initializeAndValidate()`, which starts the MCP servers and builds the tool list without a prompt, and polls `session.rpc.mcp.list()` until the server settles. It then records:

- the status and any error
- `mcp.listTools`: names, `readOnlyHint` and description length
- `mcp.oauth.probe`
- `metadata.contextInfo` and `metadata.getContextAttribution`
- every `mcp.*` and `session.mcp_*` event
- any request that reaches `onMcpAuthRequest`

The handler records each request and returns `{ kind: "cancelled" }`, so no browser opens and nothing is consented to. A baseline session with no servers gives the built-in tool cost.

- `connect` asserts that every server connects and lists at least one tool.
- `tokens` asserts that `contextInfo.mcpToolsTokens > 0` for every server.
- `login <server>` is for the owner. It starts `session.mcp.oauth.login` and prints the authorization URL. The script never opens the URL.

Redaction: the login, home and temporary directories, the `gh` token, every env-supplied secret and any `gh?_…` string are replaced, and strings over 400 characters are cut.

`contextInfo` is `null` until the session has built its tools. `initializeAndValidate()` fills it, so **no prompt was sent**, and the run used no quota.

## Results per server

|---|---|---|---|---|---|
| GitHub | `https://api.githubcopilot.com/mcp/` | `Authorization: Bearer <gh token>` (the `gh` CLI's OAuth token) | **connected** in 0.6 s | 46 (28 `readOnlyHint`) | **13,835** |
| GitHub, no header | same | none: the runtime attaches the Copilot sign-in itself | **connected** in 0.5 s | 46 | 13,945 (the longer server id adds 110) |
| Datadog | `https://mcp.datadoghq.com/api/unstable/mcp-server/mcp` (US1 site) | runtime OAuth | **needs-auth**: consent required | — | 0 |
| ClickUp | `https://mcp.clickup.com/mcp` | runtime OAuth | **needs-auth**: consent required | — | 0 |
| Snowflake | not known | — | **blocked**: no endpoint (Q-06) | — | — |

The baseline session with no MCP server had 6,969 tool-definition tokens (built-in tools) and 5,309 system tokens. `toolDefinitionsTokens` minus the baseline equals `mcpToolsTokens` exactly (20,804 − 6,969 = 13,835). Token counts are tokenized against `claude-sonnet-5` (`modelSource: "default"`): on Free, before a prompt, the runtime has no routed model and counts with its default.

### GitHub

- **The PAT path** (`gh auth token` as a Bearer header) works unattended. The probe returns `no-auth-required`, because the header is a static token and not an OAuth grant.
- **No header at all also connects.** The same URL returns 401 to an unauthenticated `curl` (`error="invalid_request"`, `resource_metadata=".../.well-known/oauth-protected-resource/mcp/"`). So the runtime attaches the Copilot user's credential to `api.githubcopilot.com` on its own. For Pica, the GitHub preset needs no secret: the Copilot sign-in is enough. That makes this the plan-agnostic default (D-16). The PAT form stays as an override (for example a fine-grained PAT, or another account).
- Runtime-side options exist for GitHub: `githubMcpToolConfig` on the session (`additionalToolsets`, `enableAllTools`, …), and the server honours `X-MCP-Toolsets`, `X-MCP-Tools`, `X-MCP-Readonly` and `X-MCP-Lockdown` request headers (seen in `access-control-allow-headers`). `X-MCP-Readonly` is the obvious lever for M-05's write-class default and is untested.
- Heaviest tools: `issue_write` 962, `pull_request_read` 672, `list_issues` 658, `pull_request_review_write` 575, `search_issues` 530 tokens.

### Datadog

The server answers 401 with `WWW-Authenticate: Bearer resource_metadata="https://mcp.datadoghq.com/.well-known/oauth-protected-resource/api/unstable/mcp-server/mcp"`. That metadata names the authorization server `https://mcp.datadoghq.com/v1/mcp`, whose RFC 8414 metadata advertises:

- authorize at `https://app.datadoghq.com/oauth2/v1/authorize` and token at `https://app.datadoghq.com/api/v2/oauth2/token`
- dynamic client registration at `https://app.datadoghq.com/api/v2/oauth2/register`
- PKCE `S256`, public clients (`token_endpoint_auth_methods_supported: ["none"]`), and scope `mcp_all`

What the runtime did:

1. During initialization it emitted `mcp.oauth_required` twice, both `reason: "initial"`. With `onMcpAuthRequest` set, each one went to the host. The spike cancelled them, which produced `mcp.oauth_completed` with `outcome: "cancelled"` and left the status at `needs-auth`. `mcp.list().host.needsAuthServers` lists the server.
2. In a separate exploratory session with **no** `onMcpAuthRequest` handler, `session.mcp.oauth.login({ serverName })` registered a client dynamically and returned an `authorizationUrl` on `app.datadoghq.com/oauth2/v1/authorize` with `response_type, client_id, state, code_challenge, code_challenge_method=S256, redirect_uri=http://127.0.0.1:<port>/, resource=<server URL>`, and no `scope`. The runtime started its loopback listener and **did not open a browser**. The URL was not opened.
3. The runtime **persisted the client registration** in `~/.copilot/mcp-oauth-config/<sha256>.json` (`serverUrl`, `authorizationServerUrl`, `clientId`, `redirectUri`, `isStatic: false`) with a `.verifier` file beside it. The owner's login will reuse that registration. The file holds no grant.

Datadog has one endpoint per site (US1 `datadoghq.com`, EU `datadoghq.eu`, US3, US5, AP1, …). Only US1 was tried, and the owner's site is not known. Datadog also accepts API and application keys as headers (`DD-API-KEY`, `DD-APPLICATION-KEY`). The spike supports that path (`PICA_S06_DATADOG_API_KEY`, `PICA_S06_DATADOG_APP_KEY`) but had no keys to try.

### ClickUp

The server answers 401 with `WWW-Authenticate: Bearer realm="MCP Server", error="invalid_token", error_description="Bearer token required", resource_metadata="https://mcp.clickup.com/.well-known/oauth-protected-resource/mcp"`. Its authorization server is `https://mcp.clickup.com`:

- authorize at `/oauth/authorize`, token at `/oauth/token`, registration at `/oauth/register`
- PKCE `S256`, and scopes `read` and `write`

The runtime behaved as it did with Datadog: one `mcp.oauth_required` (`initial`), cancelled, `needs-auth`. ClickUp is OAuth only; there is no API-key option on this endpoint.

### Snowflake

Not attempted. The URL has the form `https://<account_url>/api/v2/databases/{db}/schemas/{schema}/mcp-servers/{name}` and exists only after an admin runs `CREATE MCP SERVER` (§2.2). Per §2.2, Snowflake does not support dynamic client registration. The runtime handles that case with a static client (`McpOauthLoginRequest.clientId`/`clientSecret`/`publicClient`, or `staticClientConfig` on the auth request), or with a PAT in a header. The spike supports `PICA_S06_SNOWFLAKE_URL` and an optional `PICA_S06_SNOWFLAKE_TOKEN` (PAT, sent as Bearer).

## What the owner must do

Each server is independent: run only the lines for the servers you have.

1. **Datadog.** Find your Datadog site (the host of your Datadog web UI). For a site other than US1, export `PICA_S06_DATADOG_URL=https://mcp.<site>/api/unstable/mcp-server/mcp`. Then run `node spikes/s-06-mcp/s06.mjs login datadog`, open the printed URL, sign in and approve. The script waits 300 s (`PICA_S06_LOGIN_WAIT`) for the server to connect. As an alternative, export `PICA_S06_DATADOG_API_KEY` and `PICA_S06_DATADOG_APP_KEY`.
2. **ClickUp.** Run `node spikes/s-06-mcp/s06.mjs login clickup`, open the URL, choose the workspace and approve.
3. **Snowflake.** Answer Q-06: does the MCP server exist, what is its URL, and is the auth Snowflake OAuth, external OAuth, or PAT? Then export `PICA_S06_SNOWFLAKE_URL`, and either `PICA_S06_SNOWFLAKE_TOKEN` (a PAT with the server's role) or, for OAuth, run `login snowflake`. OAuth needs a static client (the security integration's client id and secret), which the spike does not take yet: one more spike change.
4. Run `PICA_LIVE=1 make verify UNIT=S-06`. Both live checks rerun every server, and the results file is rewritten.

## Mismatches with M-01 to M-06

Recorded for follow-ups; nothing is fixed here.

1. **OAuth is duplicated (M-03, `core/src/mcp-auth/`, `adapters/src/mcp-oauth/`).** M-03 implements its own discovery, DCR, PKCE, loopback and token refresh, with grants kept in memory. The runtime already does all of this and persists grants under `~/.copilot/`. The SDK gives Pica two clean choices:
   - (a) **Runtime-owned:** call `session.mcp.oauth.login` and show the URL. Watch `session.mcp_server_status_changed` and `mcp.oauth_completed`. The UI is Pica's; the token store is the runtime's.
   - (b) **Host-owned:** set `onMcpAuthRequest` and answer `{ kind: "token", accessToken, expiresIn }`, including `reason: "refresh"`, with `runtimeRefresh` when it is advertised.

   M-03's `loginMcpServer`/`createMcpTokenManager` fits (b) but is not wired to `onMcpAuthRequest`. Pick one in a decision; (a) removes most of M-03's adapter code, and (b) keeps tokens in the Keychain.
2. **Health is probed outside the runtime (M-06, `adapters/src/mcp-client/`).** M-06's own MCP client opens a second connection to each server and gets no OAuth bearer tokens, so an OAuth server would show `needs_auth` in Pica even after the runtime has a grant. The runtime reports the same facts per session: `session.mcp.list()` (`status`, `error`, `host.needsAuthServers`, `host.failedServers`), `session.mcp_server_status_changed`, `session.mcp_server_tools_loaded` (`toolCount`), `mcp.listTools`. The status names differ: runtime `pending | connected | needs-auth | failed | disabled | not_configured` against protocol `connecting | healthy | degraded | needs_auth | failed | stopped`.
3. **Tool names in context are `<server>-<tool>`, not `server/tool` (M-04 `token-estimate.ts`, M-05 `mcp.tool` targets).** Attribution entries read `toolDefinition:github-issue_write`. The server id is part of every tool name, so a longer id costs tokens: `github-signin` cost 110 more than `github` over 46 tools. M-05 hook targets must parse the `-` form (untested here: S-06 calls no tool).
4. **The token estimate is about 8% low (M-04).** M-04's formula on the live GitHub tools gives 12,676, against `mcpToolsTokens` 13,835 (−8.4%). Per-entry attribution sums to 13,858, 23 more than `mcpToolsTokens`. Use `contextInfo.mcpToolsTokens` (or per-server sums from `getContextAttribution`) after `initializeAndValidate()` as the real figure. Keep the estimate only for servers that are not connected yet, or recalibrate it (for example `bytes / 3.7`).
5. **`listTools` returns more than its type declares.** `McpTools` declares `name`, `description` and `ui`, but the live result also carries `inputSchema`, `outputSchema`, `annotations` and `icons`. M-04's catalog and M-05's `readOnlyHint` can be filled from the runtime instead of from M-06's own client, but the adapter must validate the fields rather than trust the type.
6. **The stdio working directory key (M-04 `session-config.ts`).** M-04 emits `cwd` for local servers; the SDK's `MCPStdioServerConfig` field is `workingDirectory`. `cwd` would be ignored.
7. **The GitHub preset needs no secret (M-02).** The Copilot sign-in is attached automatically for `api.githubcopilot.com`. M-02's GitHub preset should default to no headers, with an optional PAT secret reference. M-01's inline-secret rule is unaffected.
8. **The Datadog site is a parameter (M-02).** Its URL is `https://mcp.<site>/api/unstable/mcp-server/mcp`. ClickUp has a single URL. Snowflake needs account, database, schema and server name.
9. **Statuses Pica has no field for:** `mcp.oauth_required`/`mcp.oauth_completed` (with `requestId`, `reason`, `resourceMetadata` and the raw 401), `mcp.headers_refresh_required` (dynamic headers) and `session.mcp_server_needs_reconnect`.

## Reproduce

```sh
PICA_LIVE=1 make verify UNIT=S-06          # both live checks plus the A8 check
node spikes/s-06-mcp/s06.mjs connect        # all servers; or name some: connect github clickup
node spikes/s-06-mcp/s06.mjs tokens
node spikes/s-06-mcp/s06.mjs login datadog  # owner only: prints the consent URL
```

The script needs a Copilot CLI login, and GitHub also uses the `gh` login. Without `PICA_LIVE=1` the live checks are skipped. They never run in CI.

# S-05 · Packaging — findings

**Outcome: A7 confirmed, with a different install path from the one D-17 first assumed. The second-account check is waiting on the owner.**

- An ad-hoc signed `.app` with the hardened runtime passes `codesign --verify --deep --strict` and still verifies after a `ditto` zip and unzip. The app holds Node, a hello engine and the Copilot runtime.
- When launched, it starts its engine, and the engine answers the ping over the socket protocol.
- One entitlement is non-obvious: once `copilot-runtime` is re-signed ad-hoc, it needs `disable-library-validation`.
- **On macOS 27.2.1, a quarantined ad-hoc app cannot be approved through "Open Anyway".** The dialog offers only Move to Trash and Done, and Privacy & Security shows no Open Anyway button (owner test, below).
- What works is installing it with no quarantine. Either clear the attribute before the first launch, or download with `curl`, which sets none. The recommended install path is in [Install path](#install-path-for-unnotarized-builds). The manual check is that path on a clean account.

## What was built

`spikes/s-05-packaging/` (throwaway):

- `launcher/main.swift` is the app's main executable, standing in for A-01. It starts `Contents/Helpers/node` with the engine, waits for the `{"ready":true,...}` line on stdout, and connects to the Unix socket. It then sends `engine.hello`, `engine.health` and `spike.probe`. It writes the result to `~/Library/Logs/PicaS05/last-run.json` and shows it in an alert, unless it was given `--headless`.
- `engine/hello-engine.mjs` speaks the engine's wire protocol (E-05): NDJSON JSON-RPC 2.0 over a Unix socket, with `engine.hello` required first and the same ready line. It answers `engine.hello` and `engine.health` with the real result shapes. `spike.probe` spawns the bundled `copilot-runtime` the way the SDK does (`--headless --no-auto-update --stdio --no-auto-login`) and sends it the SDK's `ping`. It also opens `node:sqlite`, the store's driver (E-03).
- `install.sh <zip URL> <sha256> [destination]` is the prototype install script (see [Install path](#install-path-for-unnotarized-builds)).
- `run.sh build|signatures|quarantine|report`:
  - `build` assembles `out/Pica S-05.app`, signs it inside out, and zips it with `ditto -c -k --keepParent`.
  - `signatures` is the mapped check.
  - `quarantine` simulates the download on this account and tests both install paths.
  - `report` prints sizes and the designated requirement.

Bundle layout:

```
Pica S-05.app/Contents/
  Info.plist                       dev.pica.spike.s05, LSMinimumSystemVersion 26.0
  MacOS/PicaS05                    launcher (Swift, arm64)
  Helpers/node                     Node 22.17.0 (copied from the build machine)
  Resources/engine/hello-engine.mjs
  Resources/copilot/               @github/copilot-sdk-darwin-arm64 1.0.28, layout unchanged
    prebuilds/darwin-arm64/{copilot-runtime, runtime.node, libOneAuthInterop.dylib, msal-node-runtime.node, libmsalruntime_arm64.dylib}
    ripgrep/…/rg  tgrep/…/tgrep  plugins/computer-use/{computer-use-mcp, Copilot Computer Use.app}
```

The Copilot package stays whole under `Resources/` because `copilot-runtime` finds `runtime.node`, `rg` and `tgrep` relative to itself. The package also mixes code with JS and JSON, and that is not allowed under `Contents/Helpers` or `Contents/Frameworks`. Code in `Resources` is sealed as a resource, so `--deep` verification of the app does not descend into it. For that reason `run.sh signatures` also verifies each Mach-O on its own. The engine finds the runtime through `COPILOT_CLI_PATH`, which the SDK already honours. Without it, the SDK would resolve the platform package from `node_modules`, and that lookup does not exist in the app.

## Signing

`codesign --force --sign - --options runtime --timestamp=none`, applied inside out:

1. Every Mach-O file, deepest path first. There are 11: the launcher, Node, `copilot-runtime`, `runtime.node`, 2 dylibs, `msal-node-runtime.node`, `rg`, `tgrep`, `computer-use-mcp`, and the Computer Use app's executable.
2. Nested `.app` bundles (`Copilot Computer Use.app`).
3. The app.

| Binary | Entitlements | Why |
|---|---|---|
| `Helpers/node` | `com.apple.security.cs.allow-jit` | V8's JIT under the hardened runtime. `allow-jit` alone is enough: no `allow-unsigned-executable-memory` and no `disable-library-validation`. The engine loads no native addons, and `node:sqlite` is built in. |
| `copilot-runtime` | `com.apple.security.cs.disable-library-validation` | It `dlopen`s `runtime.node`. Library validation only accepts libraries from Apple or from the same Team ID, and an ad-hoc signature has no Team ID. Without this entitlement the ping fails with `failed to load runtime cdylib …/runtime.node: dlopen failed`. GitHub's own signature carries no entitlements, because both files share GitHub's Team ID. |
| everything else | none | |

The original Node binary (Developer ID, Node.js Foundation) carries six entitlements, including `get-task-allow` and `allow-dyld-environment-variables`. Re-signing drops them, which is what we want: notarization rejects `get-task-allow`.

An alternative was tested once by hand, not scripted: keep GitHub's Developer ID signatures on the Copilot files and re-sign only our own code. `--deep --strict` passes on the app and the ping succeeds. `copilot-runtime` then needs no entitlement, because GitHub signed both it and `runtime.node`, and nothing of GitHub's loads into our processes. The spike re-signs everything because D-17 says to, but keeping vendor signatures is the better option once notarization arrives (see below).

## Gatekeeper and quarantine

### Owner test (macOS 27.2.1, the owner's own account, developer tools installed)

Two fresh copies were extracted from `out/Pica-S05.zip` into `~/Downloads/pica-s05-test/`:

| Copy | Result |
|---|---|
| `1-as-downloaded`: whole tree quarantined (`0083`) | "“Pica S-05” Not Opened — Apple could not verify “Pica S-05” is free of malware…", with only **Move to Trash** and **Done**. On an earlier attempt, System Settings › Privacy & Security showed **no Open Anyway** button. The Open Anyway route that D-17 assumed does not exist for this ad-hoc signed app on macOS 27. |
| `2-quarantine-cleared`: `xattr -dr com.apple.quarantine` run before the first launch | Launched, and the engine answered the ping: `ok: true`, `pong: s05`, Node v22.17.0, SQLite 3.50.0. No translocation: the bundle path was the Downloads folder. |

### Simulated on the build machine (`run.sh quarantine`)

The script copies the zip and sets `com.apple.quarantine` to `0083;<time>;Safari;<uuid>`. It then extracts it with `ditto -x -k`. Like Archive Utility, `ditto` copies the quarantine onto every extracted item (it drops the agent name). Each variant gets a fresh extraction:

| Variant | Result |
|---|---|
| Every item quarantined, as downloaded | Signature verifies, but `spctl --assess --type execute` says **rejected**. Running `Contents/MacOS/PicaS05` straight from a shell is held too: the process sits at `_dyld_start`, and Gatekeeper puts its "Not Opened" dialog on screen. So Terminal is not a way around it. This probe is off by default (`S05_PROBE_BLOCK=1`) because of the dialog. |
| Path (a): `xattr -dr com.apple.quarantine` before the first launch | **Ping answered.** This matches the owner's copy 2. |
| Path (b): `install.sh` fetches the zip with `curl` from a local HTTP server | Wrong checksum: **refused**, nothing installed. Right checksum: installed with no quarantine on any item, and **ping answered**. |

Measured once by hand, not scripted. With the bundle directory, `Contents`, the main executable, `Info.plist` and `CodeResources` cleared, the engine still ran although Node and `copilot-runtime` stayed quarantined. Quarantined helpers spawned by an allowed app are not gated one by one. A copy with the user-approved flag (`00c3`) on every item also ran.

Gatekeeper caches its verdict per file. Once a copy has been blocked, it stayed blocked here even after `xattr -dr com.apple.quarantine`, while identical bytes at a new path ran. So the quarantine has to be cleared **before the first launch**. A user who has already double-clicked the app should delete it and install again. `syspolicy_check distribution` reports the two expected failures: "Adhoc Signed App" (warning) and "Notary Ticket Missing" (fatal).

`curl` sets no quarantine: a file it fetched carries only `com.apple.provenance`. Only apps that opt in with `LSFileQuarantineEnabled`, sandboxed apps, and the browsers add `com.apple.quarantine`.

## Install path for unnotarized builds

Options:

- **(a) A documented step:** download in the browser, unzip, move to `/Applications`, then `xattr -dr com.apple.quarantine /Applications/Pica.app` before the first launch.
  - Pro: no script to trust, and it works with the plain release asset.
  - Con: it is easy to double-click first, and Gatekeeper's per-file cache then makes the user start over. There is also no integrity check beyond HTTPS.
- **(b) An install script:** `curl -fsSL https://github.com/0zean/pica/releases/latest/download/install.sh | sh`. The script downloads the zip with `curl` (no quarantine), checks its SHA-256 against the value published with the release, runs `codesign --verify --deep --strict`, and installs into `/Applications` (or `~/Applications` when `/Applications` is not writable).
  - Pro: one paste, no opportunity to launch early, a checksum, and the same command updates a broken install.
  - Con: "pipe to sh" asks users to trust the script, and the checksum comes from the same release, so it catches corruption and truncation, not a compromised release. Both routes rest on GitHub's HTTPS either way, which is the trust a notarized build would replace.
- **(c) Both.**

**Recommendation: (c), with the script as the primary route.** The script is the one-line install in the README and the release notes. The documented `xattr` step is the fallback for people who downloaded the zip in a browser, and it is the recovery for "Not Opened": delete the app, unzip again, run `xattr` before opening. A prototype is in `spikes/s-05-packaging/install.sh`. It uses only base-system tools (`curl`, `shasum`, `ditto`, `codesign`, `xattr`), takes `<zip URL> <sha256> [destination]`, and allows HTTPS only. H-06's version should read the checksum from a `SHA256SUMS` asset of the same release.

Either route needs release assets that can be downloaded without signing in. `0zean/pica` is private today, so H-06 has two choices: publish releases from a public repository (or make this one public), or have the script authenticate with `gh release download`, which would bring back a developer-tool dependency.

**Sparkle updates do not reintroduce quarantine.** Sparkle runs inside Pica, which is neither sandboxed nor opted in to `LSFileQuarantineEnabled`. So Sparkle's own download carries no `com.apple.quarantine`. Sparkle's installer also releases quarantine on the extracted update before replacing the app (`SUFileManager`'s `releaseItemFromQuarantine`). Once installed, a build stays installable through updates. H-06's N → N+1 update check should also assert that the updated bundle has no `com.apple.quarantine`.

On the build account:

- [ ] `spikes/s-05-packaging/run.sh quarantine` passes. It also builds `spikes/s-05-packaging/out/Pica-S05.zip`.
- [ ] Run `shasum -a 256 spikes/s-05-packaging/out/Pica-S05.zip` and note the hash.
- [ ] The repository is private, so a release asset needs a GitHub sign-in to download. Instead, put the files where the test account can read them:

  ```sh
  cp spikes/s-05-packaging/out/Pica-S05.zip spikes/s-05-packaging/install.sh /Users/Shared/
  ```

  A `file://` fetch by `curl` sets no quarantine, the same as an HTTPS one, so the script behaves as it would from a release.

On the second account (a standard user is the realistic case):

- [ ] Confirm there are no developer tools: `xcode-select -p` fails or offers to install them (do not install), and `command -v node` prints nothing.
- [ ] **Path (b), the install script:** run `S05_ALLOW_INSECURE=1 sh /Users/Shared/install.sh file:///Users/Shared/Pica-S05.zip <hash>`. It prints `Installed …/Pica S-05.app`, in `~/Applications` for a standard user. Then:
  - `xattr -p com.apple.quarantine ~/Applications/"Pica S-05.app"` reports no such xattr.
  - Double-click the app. It opens with no Gatekeeper dialog and shows the alert **"Engine answered the ping"**. The JSON shows `"ok" : true`, `"engineVersion" : "0.0.0-s05"`, `"message" : "pong: s05"` and a `sqlite` version.
- [ ] **Path (a), the documented step:**
  1. Copy `/Users/Shared/Pica-S05.zip` to `~/Downloads`. Give it the quarantine a Safari download would get with `xattr -w com.apple.quarantine "0083;$(printf %x $(date +%s));Safari;$(uuidgen)" ~/Downloads/Pica-S05.zip`. If the account can sign in to GitHub, a Safari download of a release asset works too. Check that `xattr -p com.apple.quarantine ~/Downloads/Pica-S05.zip` prints a value starting `008`.
  2. Unzip it in Finder and move the app to `~/Applications/pica-a/`.
  3. Run `xattr -dr com.apple.quarantine ~/Applications/pica-a/"Pica S-05.app"` **before** opening it.
  4. Double-click the app: same alert, no dialog.
- [ ] `cat ~/Library/Logs/PicaS05/last-run.json` shows `"ok" : true`, and `bundle` is the install path, not `/private/var/folders/…/AppTranslocation/…`.
- [ ] Record the macOS version and any prompt that appeared, and remove the two files from `/Users/Shared`. Tick the manual check in `PLAN.md` §10 and set S-05 to `done` in §12.

If the alert says "Engine did not answer", the JSON's `error` or `probe.copilot.stderr` says which step failed. That outcome means A7 is false for clean machines, and the fallback in §2.4 applies.

Node and `runtime.node` make up most of the size. A universal (x64 + arm64) build would roughly double it, so H-06 should ship arm64 only unless Intel support is asked for. Node's size could be cut with a custom build (small ICU), but that was not tried.

## Keychain prompts with ad-hoc signatures (§11.1)

An ad-hoc signature's designated requirement is the main executable's code-directory hash: `designated => cdhash H"6d36…cc04"`. That hash covers `Info.plist` and the sealed-resources file. Two builds from identical inputs give the same requirement. Changing one byte of `hello-engine.mjs` and re-signing gives a new one (`108a…27b6`). So every release has a new designated requirement.

What this means for D-10 and M-03:

- Without a Team ID there is no `keychain-access-groups` entitlement, so Pica cannot use the data-protection keychain. Items go in the login keychain, and their access control lists name the app by its designated requirement.
- After each update, the first read of each item shows "Pica wants to use your confidential information stored in "…" in your keychain". The user has to click Always Allow again, once per item, per release.
- A fixed requirement such as `codesign -s - -r='designated => identifier "dev.pica.app"'` works, and `--deep --strict` passes. It is spoofable, though: any program signed with that identifier would match. Do not use it for secrets.
- For v1: accept one prompt per item per update. M-03 should keep secrets in as few Keychain items as possible (one item holding a JSON map, say), so an update costs one prompt, not one per secret. The install guide and release notes should say the prompt is expected.
- A Developer ID removes the problem. The requirement becomes `identifier … and anchor apple generic and certificate leaf[subject.OU] = <team>`, which stays the same across releases.

## What changes once a Developer ID exists (H-06)

- Signing: replace `-s -` with `-s "Developer ID Application: …"` and `--timestamp`; notarization requires a secure timestamp. Keep `--options runtime`. Script nothing else differently.
- Notarization: `xcrun notarytool submit Pica.zip --keychain-profile … --wait`, then `xcrun stapler staple Pica.app`, then re-zip. The stapled ticket lets a quarantined download open normally, so the install shrinks to "unzip and open". The install script and the `xattr` step stay only for ad-hoc builds.
- Entitlements: keep `allow-jit` on Node, and never ship `get-task-allow`. Keep GitHub's Developer ID signatures on the Copilot package rather than re-signing it: notarization accepts other teams' Developer ID code, and `copilot-runtime` then needs no `disable-library-validation`. If we do re-sign it with our Team ID, the entitlement is also unnecessary, because the runtime and its library share a team.
- Keychain: designated requirements become stable (above), and the data-protection keychain becomes available if wanted.
- Sparkle: its EdDSA signatures are independent of Apple signing (D-17). Sparkle also compares the update's code signature with the running app's, though, and as we understand it, it lets one update change either the Apple signing identity or the EdDSA key, never both. H-06 should test the first Developer ID release as an update from an ad-hoc release, with the EdDSA key unchanged.

## Notes for later units

- **A-01**: run the engine from `Contents/Helpers/node` with the bundled engine under `Resources`, and set `COPILOT_CLI_PATH` to the bundled `copilot-runtime`. Never write inside the bundle: translocated apps run from a read-only path. Put the socket under the per-user temporary directory or Application Support, within `sun_path`'s 104 bytes.
- **H-06**: `run.sh`'s `sign` function is the release workflow's signing step. The checks in `run.sh signatures` are H-06's first check. Sign nested `.app` bundles as bundles.
- The Copilot package's computer-use plugin is a separate app (`Copilot Computer Use.app`, 9.8 MB) that Pica does not use. H-06 can test whether the runtime tolerates dropping it.

## Reproduce

Apple M2 Pro, macOS 27.2.1, Xcode 27.2 (Swift 6.4.2), Node 22.17.0, `@github/copilot-sdk` 1.0.28.

```sh
make verify UNIT=S-05
spikes/s-05-packaging/run.sh quarantine   # download simulation + both install paths; S05_PROBE_BLOCK=1 adds the blocked-launch probe (shows a dialog)
spikes/s-05-packaging/run.sh report
```

The spike is not part of the default `make verify`. It needs Xcode's `swiftc` and `codesign`, and it takes about 15 s.

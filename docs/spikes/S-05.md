# S-05 · Packaging — findings

**Outcome: A7 confirmed on the build machine; the second-account check is waiting on the owner.** An ad-hoc signed `.app` with the hardened runtime, holding Node, a hello engine and the Copilot runtime, passes `codesign --verify --deep --strict` and still verifies after a `ditto` zip and unzip. When launched, it starts its engine, and the engine answers the ping over the socket protocol. When quarantined as a browser download would be, Gatekeeper rejects it until the user approves it. Once the bundle is cleared, the quarantined nested helpers (Node, `copilot-runtime`) run without any further prompt. This needs one non-obvious entitlement: re-signing `copilot-runtime` ad-hoc requires `disable-library-validation`. The real "Open Anyway" flow on a clean account is the manual check below.

## What was built

`spikes/s-05-packaging/` (throwaway):

- `launcher/main.swift` is the app's main executable, standing in for A-01. It starts `Contents/Helpers/node` with the engine, waits for the `{"ready":true,...}` line on stdout, and connects to the Unix socket. It then sends `engine.hello`, `engine.health` and `spike.probe`. It writes the result to `~/Library/Logs/PicaS05/last-run.json` and shows it in an alert, unless it was given `--headless`.
- `engine/hello-engine.mjs` speaks the engine's wire protocol (E-05): NDJSON JSON-RPC 2.0 over a Unix socket, with `engine.hello` required first and the same ready line. It answers `engine.hello` and `engine.health` with the real result shapes. `spike.probe` spawns the bundled `copilot-runtime` the way the SDK does (`--headless --no-auto-update --stdio --no-auto-login`) and sends it the SDK's `ping`. It also opens `node:sqlite`, the store's driver (E-03).
- `run.sh build|signatures|quarantine|report`:
  - `build` assembles `out/Pica S-05.app`, signs it inside out, and zips it with `ditto -c -k --keepParent`.
  - `signatures` is the mapped check.
  - `quarantine` simulates the download on this account.
  - `report` prints sizes and the designated requirement.

Bundle layout:

```
Pica S-05.app/Contents/
  Info.plist                       dev.pica.spike.s05, LSMinimumSystemVersion 26.0
  MacOS/PicaS05                    launcher (Swift, arm64)
  Helpers/node                     Node 22.17.0 (copied from the build machine)
  Resources/engine/hello-engine.mjs
  Resources/copilot/               @github/copilot-sdk-darwin-arm64 1.0.28, layout unchanged
    prebuilds/darwin-arm64/{copilot-runtime, runtime.node, libOneAuthInterop.dylib, msal-node-runtime.node, libmsalruntime_arm64.dylib}
    ripgrep/…/rg  tgrep/…/tgrep  plugins/computer-use/{computer-use-mcp, Copilot Computer Use.app}
```

The Copilot package stays whole under `Resources/` because `copilot-runtime` finds `runtime.node`, `rg` and `tgrep` relative to itself. The package also mixes code with JS and JSON, and that is not allowed under `Contents/Helpers` or `Contents/Frameworks`. Code in `Resources` is sealed as a resource, so `--deep` verification of the app does not descend into it. For that reason `run.sh signatures` also verifies each Mach-O on its own. The engine finds the runtime through `COPILOT_CLI_PATH`, which the SDK already honours. Without it, the SDK would resolve the platform package from `node_modules`, and that lookup does not exist in the app.

## Signing

`codesign --force --sign - --options runtime --timestamp=none`, applied inside out:

1. Every Mach-O file, deepest path first. There are 11: the launcher, Node, `copilot-runtime`, `runtime.node`, 2 dylibs, `msal-node-runtime.node`, `rg`, `tgrep`, `computer-use-mcp`, and the Computer Use app's executable.
2. Nested `.app` bundles (`Copilot Computer Use.app`).
3. The app.

| Binary | Entitlements | Why |
|---|---|---|
| `Helpers/node` | `com.apple.security.cs.allow-jit` | V8's JIT under the hardened runtime. `allow-jit` alone is enough: no `allow-unsigned-executable-memory` and no `disable-library-validation`. The engine loads no native addons, and `node:sqlite` is built in. |
| `copilot-runtime` | `com.apple.security.cs.disable-library-validation` | It `dlopen`s `runtime.node`. Library validation only accepts libraries from Apple or from the same Team ID, and an ad-hoc signature has no Team ID. Without this entitlement the ping fails with `failed to load runtime cdylib …/runtime.node: dlopen failed`. GitHub's own signature carries no entitlements, because both files share GitHub's Team ID. |
| everything else | none | |

The original Node binary (Developer ID, Node.js Foundation) carries six entitlements, including `get-task-allow` and `allow-dyld-environment-variables`. Re-signing drops them, which is what we want: notarization rejects `get-task-allow`.

An alternative was tested once by hand, not scripted: keep GitHub's Developer ID signatures on the Copilot files and re-sign only our own code. `--deep --strict` passes on the app and the ping succeeds. `copilot-runtime` then needs no entitlement, because GitHub signed both it and `runtime.node`, and nothing of GitHub's loads into our processes. The spike re-signs everything because D-17 says to, but keeping vendor signatures is the better option once notarization arrives (see below).

## Gatekeeper and quarantine (simulated on the build machine)

`run.sh quarantine` copies the zip and sets `com.apple.quarantine` to `0083;<time>;Safari;<uuid>`. It then extracts the zip with `ditto -x -k`. Like Archive Utility, `ditto` copies the quarantine onto every extracted item (it drops the agent name). Results:

| Variant (fresh extraction each) | Result |
|---|---|
| Every item quarantined, as downloaded | Signature verifies. `spctl --assess --type execute` says **rejected**. Running `Contents/MacOS/PicaS05` straight from a shell is held too: the process sits at `_dyld_start`, and Gatekeeper puts its "Not Opened" dialog on screen. So Terminal is not a way around Gatekeeper. This probe is off by default (`S05_PROBE_BLOCK=1`) because of the dialog. |
| Bundle directory, `Contents`, main executable, `Info.plist` and `CodeResources` cleared; Node, `copilot-runtime` and everything else still quarantined | **Ping answered**, Copilot `pong: s05`. Quarantined helpers spawned by an allowed app are not gated one by one. |
| Every item quarantined with the user-approved flag (`00c3`) | **Ping answered.** |

Gatekeeper caches its verdict per file. Once a copy has been blocked, it stays blocked even after `xattr -dr com.apple.quarantine`, while identical bytes at a new path run. That is why each variant gets its own extraction. It also means a tester who has hit the block has to approve it through System Settings: clearing the attribute is not enough.

What the simulation does not cover: the real approval is stored by `syspolicyd`, and setting it here would change a security setting. It is the manual check. `syspolicy_check distribution` reports the two expected failures: "Adhoc Signed App" (warning) and "Notary Ticket Missing" (fatal).

## Install steps (owner's manual check, and the draft of the install guide)

On the build account:

- [ ] `spikes/s-05-packaging/run.sh signatures` passes (it also builds `spikes/s-05-packaging/out/Pica-S05.zip`).
- [ ] Get the zip to the test account so that it arrives quarantined:
  - Preferred: attach it to a throwaway pre-release, with `gh release create s05-test --prerelease --title "S-05 test" spikes/s-05-packaging/out/Pica-S05.zip`, and download it in Safari on the test account. Delete the release afterwards with `gh release delete s05-test --cleanup-tag`.
  - Otherwise: copy it to `/Users/Shared`. On the test account, copy it to `~/Downloads` and run `xattr -w com.apple.quarantine "0083;$(printf %x $(date +%s));Safari;$(uuidgen)" ~/Downloads/Pica-S05.zip`.

On the second account (a standard user is the realistic case):

- [ ] Confirm there are no developer tools: `xcode-select -p` fails or offers to install the tools, and `command -v node` prints nothing. Do not install the tools when prompted.
- [ ] `xattr -p com.apple.quarantine ~/Downloads/Pica-S05.zip` prints a value starting `008`.
- [ ] Double-click the zip in Finder. Move `Pica S-05.app` to `~/Applications`, creating the folder if needed, or to `/Applications` if the account is an admin.
- [ ] Double-click the app. Expect "“Pica S-05” Not Opened" ("Apple could not verify…"). Click **Done**, not Move to Trash. macOS 15 and later no longer offers Control-click › Open as a bypass.
- [ ] Open System Settings › Privacy & Security and scroll to Security. Next to "“Pica S-05” was blocked…", click **Open Anyway** and authenticate. Note whether an administrator name and password were required.
- [ ] Double-click the app again and choose **Open Anyway** in the confirmation. Expect an alert titled **"Engine answered the ping"** whose JSON shows `"ok" : true`, `"engineVersion" : "0.0.0-s05"`, `"message" : "pong: s05"` and a `sqlite` version. Click OK.
- [ ] `cat ~/Library/Logs/PicaS05/last-run.json` shows the same `"ok" : true`. Note the `bundle` path: a path under `/private/var/folders/…/AppTranslocation/` means the app ran translocated.
- [ ] Double-click the app once more. It opens with no Gatekeeper prompt.
- [ ] Record the macOS version, whether an admin password was needed, any other prompt (for example for `node` or `copilot-runtime`), and the translocation path. Then tick the manual check in `PLAN.md` §10 and set S-05 to `done` in §12.

If the alert says "Engine did not answer", the JSON's `error` or `probe.copilot.stderr` says which step failed. That outcome means A7 is false for clean machines, and the fallback in §2.4 applies.

## Bundle size

Measured with `run.sh report`, arm64 only:

| | Size |
|---|---|
| App on disk | 249 MB |
| Zip (`ditto -c -k`) | 96 MB (100,258,260 bytes) |
| `Helpers/node` | 105 MB |
| `Resources/copilot` | 144 MB, of which `runtime.node` is ~98 MB, `libOneAuthInterop.dylib` 12 MB, `libmsalruntime_arm64.dylib` 6.8 MB, Computer Use plugin 9.8 MB, `tgrep` 6 MB, `rg` 4.3 MB, schemas 3.6 MB |
| Hello engine | 6 KB. The real engine bundled with esbuild should be a few MB more. |

Node and `runtime.node` make up most of the size. A universal (x64 + arm64) build would roughly double it, so H-06 should ship arm64 only unless Intel support is asked for. Node's size could be cut with a custom build (small ICU), but that was not tried.

## Keychain prompts with ad-hoc signatures (§11.1)

An ad-hoc signature's designated requirement is the main executable's code-directory hash: `designated => cdhash H"6d36…cc04"`. That hash covers `Info.plist` and the sealed-resources file. Two builds from identical inputs give the same requirement. Changing one byte of `hello-engine.mjs` and re-signing gives a new one (`108a…27b6`). So every release has a new designated requirement.

What this means for D-10 and M-03:

- Without a Team ID there is no `keychain-access-groups` entitlement, so Pica cannot use the data-protection keychain. Items go in the login keychain, and their access control lists name the app by its designated requirement.
- After each update, the first read of each item shows "Pica wants to use your confidential information stored in "…" in your keychain". The user has to click Always Allow again, once per item, per release.
- A fixed requirement such as `codesign -s - -r='designated => identifier "dev.pica.app"'` works, and `--deep --strict` passes. It is spoofable, though: any program signed with that identifier would match. Do not use it for secrets.
- For v1: accept one prompt per item per update. M-03 should keep secrets in as few Keychain items as possible (one item holding a JSON map, say) so an update costs one prompt, not one per secret. The install guide should say the prompt is expected.
- A Developer ID removes the problem. The requirement becomes `identifier … and anchor apple generic and certificate leaf[subject.OU] = <team>`, which stays the same across releases.

## What changes once a Developer ID exists (H-06)

- Signing: replace `-s -` with `-s "Developer ID Application: …"` and `--timestamp`; notarization requires a secure timestamp. Keep `--options runtime`. Script nothing else differently.
- Notarization: `xcrun notarytool submit Pica.zip --keychain-profile … --wait`, then `xcrun stapler staple Pica.app`, then re-zip. The stapled ticket removes the Open Anyway steps, so the install steps above shrink to "unzip and open".
- Entitlements: keep `allow-jit` on Node, and never ship `get-task-allow`. Keep GitHub's Developer ID signatures on the Copilot package rather than re-signing it: notarization accepts other teams' Developer ID code, and `copilot-runtime` then needs no `disable-library-validation`. If we do re-sign it with our Team ID, the entitlement is also unnecessary, because the runtime and its library share a team.
- Keychain: designated requirements become stable (above), and the data-protection keychain becomes available if wanted.
- Sparkle: its EdDSA signatures are independent of Apple signing (D-17). Sparkle also compares the update's code signature with the running app's, though, and as we understand it, it lets one update change either the Apple signing identity or the EdDSA key, never both. H-06 should test the first Developer ID release as an update from an ad-hoc release, with the EdDSA key unchanged.

## Notes for later units

- **A-01**: run the engine from `Contents/Helpers/node` with the bundled engine under `Resources`, and set `COPILOT_CLI_PATH` to the bundled `copilot-runtime`. Never write inside the bundle: translocated apps run from a read-only path. Put the socket under the per-user temporary directory or Application Support, within `sun_path`'s 104 bytes.
- **H-06**: `run.sh`'s `sign` function is the release workflow's signing step. The checks in `run.sh signatures` are H-06's first check. Sign nested `.app` bundles as bundles.
- The Copilot package's computer-use plugin is a separate app (`Copilot Computer Use.app`, 9.8 MB) that Pica does not use. H-06 can test whether the runtime tolerates dropping it.

## Reproduce

Apple M2 Pro, macOS 27.2.1, Xcode 27.2 (Swift 6.4.2), Node 22.17.0, `@github/copilot-sdk` 1.0.28.

```sh
make verify UNIT=S-05
spikes/s-05-packaging/run.sh quarantine   # simulation; S05_PROBE_BLOCK=1 adds the blocked-launch probe (shows a dialog)
spikes/s-05-packaging/run.sh report
```

The spike is not part of the default `make verify`. It needs Xcode's `swiftc` and `codesign`, and it takes about 15 s.

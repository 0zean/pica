# S-04 · Multi-root access — findings

**Outcome: A6 confirmed.** A session whose `workingDirectory` is repo A reads a file in repo B once the host approves the runtime's `read` permission request. No symlink root and no engine-only fallback are needed. Passing B in `additionalDirectories` also works and halves the prompts, but does not remove them. A `preToolUse` hook built on R-07's shell-path parser blocks writes into B through both the patch tool and a shell redirect, and B stays untouched. Two sessions with different working directories run concurrently on one client without cross-talk. Tested on Copilot Free (`auto`, routed to `gpt-6-luna`), SDK 1.0.28, with 16 short prompts in all (10 while building the spike, 6 in the final `make verify UNIT=S-04`).

## What was built

`spikes/s-04-multi-root/s04.mjs` (throwaway). Like S-01 it imports the pinned SDK from the adapter's `node_modules`. It also imports R-07's `shellPaths` from `engine/packages/core/src/policy/shell-paths.ts`, so the fence uses the parser Pica ships (it runs with `node --experimental-strip-types`).

Each live mode creates two fixture git repos, A and B, under a fresh `~/.pica-s04-*` directory, and deletes it on exit. The fixtures are deliberately **not** under the OS temporary directory: the first run put them there, and no permission request fired at all, because the runtime grants temporary storage to every session (see the sandbox notes below). Saved logs ([`S-04-read.json`](S-04-read.json), [`S-04-write.json`](S-04-write.json), [`S-04-concurrent.json`](S-04-concurrent.json)) replace the repo paths with `<repoA>`/`<repoB>`, the home directory with `~`, the login with `<login>`, and anything shaped like a GitHub token with `<token>`. They drop the runtime's internal `model.*` events and cut strings over 400 characters.

| Mode | Prompts | What it asserts |
|---|---|---|
| `read` | 2 | `Read the file <repoB>/notes.txt …` from a session rooted in A, first with no grant, then with `additionalDirectories: [B]`. The permission handler approves `read` requests inside A or B once (`approve-once`) and refuses the rest. Asserts the reply holds B's random token and that a `read` request named B |
| `write` | 2 | A session rooted in A, with B in `additionalDirectories`, is asked to create `<repoB>/edit.txt` with its file tool and then to run `echo pica > <repoB>/shell.txt`. Asserts the hook denied both, the hook did not throw, and `git status` in B is empty with neither file present |
| `concurrent` | 2 (parallel) | Sessions rooted in A and B on one `CopilotClient`, each asked to read `marker.txt` in its own directory at the same time. Asserts distinct session ids, overlapping turns, each reply holds only its own token, every hook and permission call carries its own session id and working directory, and no event of one session names the other's repo |
| `guard` | 0 | Offline: which shell writes `shellPaths` sees and which it misses |

## Read outside the working directory (A6)

The mechanism is a **permission request**. The `view` call reaches `onPreToolUse` first (`toolName: "view"`, `toolArgs: { path: "<repoB>/notes.txt" }`, `workingDirectory: "<repoA>"`). The runtime then calls `onPermissionRequest` with:

```json
{ "kind": "read", "intention": "Read file: <repoB>/notes.txt", "path": "<repoB>/notes.txt" }
```

Approving with `{ kind: "approve-once" }` lets the read through, and the reply contains B's token.

| Variant | `read` requests per `view` of B | Result |
|---|---|---|
| No grant | 2, same path, both approved | read succeeds |
| `additionalDirectories: [B]` | 1 | read succeeds |
| Read of `marker.txt` inside the session's own `workingDirectory` (`concurrent` run) | 1 | read succeeds |

So `additionalDirectories` is not a grant that skips the host. Even a file inside the working directory raised a `read` request. The likely reason is that the fixture folders are not trusted (`trustWorkingDirectory` was not set), but the spike did not isolate it. Refusing the request (`reject`) is what blocks a read. The handler is therefore the place where reference roots are enforced for the runtime's own tools.

### Sandbox notes

- The shell ran with `toolTelemetry.properties.sandboxApplied: "false"`. With no `sandboxConfig`, the runtime does not use an OS sandbox, and only the hook and the permission handler stand between a command and the disk.
- The SDK's `SandboxConfig` (`sessionConfig.sandboxConfig`, `userPolicy.filesystem.readonlyPaths`/`readwritePaths`) auto-grants the working directory, temporary storage, session log paths and toolchain directories. That is why fixtures under `$TMPDIR` produced no request. Pica's own worktrees under `~/Pica/` are not covered by those grants, but a session must never be rooted in a temporary directory if the permission handler is meant to see its reads.
- The sandbox was not turned on in this spike. It is the obvious defence in depth for shell writes (see the mismatches below) and is left for a follow-up.

## Writes to B are blocked by the hook

The hook is R-07's rule in a few lines: for `bash`, every `shellPaths(command, workingDirectory)` entry (the working directory, `cd` targets, redirect and `tee` targets) must be inside a write root, and an unknown path counts as outside. For file tools, every written path must be inside a write root. Denied calls return `{ permissionDecision: "deny", permissionDecisionReason: "Blocked by Pica: … is outside the write roots." }`.

| Call | Hook | Permission request | Tool result |
|---|---|---|---|
| `apply_patch` with `*** Add File: <repoB>/edit.txt` | deny | none | `Denied by preToolUse hook: Blocked by Pica: <repoB>/edit.txt is outside the write roots.` |
| `bash` `echo pica > <repoB>/shell.txt` | deny | none | `Denied by preToolUse hook: Blocked by Pica: write target <repoB>/shell.txt is outside the write roots.` |

A hook deny ends the call before the runtime asks for permission. The model reported both as blocked and did not try another route (the prompt asked it not to). B's `git status --porcelain --untracked-files=all` was empty.

### Two failures on the way, both findings

1. **A hook that throws allows the call.** The first `write` run had a bug in the spike (the hook read a `const` declared later in the module). The SDK's `_handleHooksInvoke` catches any hook error and returns `undefined`, which means "no decision". The runtime then asked for permission as usual, the permission handler approved the shell command, and `echo pica > <repoB>/shell.txt` **wrote into B**. The patch was stopped only because the permission handler refused writes outside A. The adapter's `bridgeHooks` already turns a throwing Pica hook into a deny. But its `ledger.claimForPre(...)` call runs before that `try`, so a throw there would still fail open.
2. **The model used `apply_patch`, not `create`/`edit`.** Its argument is the raw patch text (a string), not an object with `path`. A path-argument check finds no path in it. The spike parses the `*** Add File:` / `*** Update File:` / `*** Delete File:` / `*** Move to:` headers and denies a known write tool whose paths it cannot read.

Also seen: the runtime's own `tool.execution_start.shellToolInfo.possiblePaths` listed `<repoB>/shell.txt`, but the `shell` permission request for the same call had `possiblePaths: []`, with `hasWriteFileRedirection: true`. Neither the hook input nor the permission request can be relied on to name the paths a shell command writes.

## Two concurrent sessions on one client

Both turns ran inside the same 3.2 s window on one `CopilotClient`. Session A replied with A's token and session B with B's. Every hook input had its own `sessionId` and `workingDirectory`, every permission call had its own `invocation.sessionId`, and no event of either session mentioned the other's repo. Per-session `onPermissionRequest`, `hooks` and `onEvent` are therefore safe to bind to one Pica session each, which is what the adapter does.

## Compared with R-07 and R-08

Recorded for follow-up units; not fixed here.

1. **`shellPaths` misses argument writes.** The offline `guard` mode shows that it catches `echo x > B/f`, `… | tee B/f` and `cd B && touch f`, but misses `touch B/f`, `cp README.md B/f`, `python3 -c "open('B/f','w')"` and `git -C B commit -am x`. These all run in a working directory inside the write root and write outside it. R-07's rule is a redirect and working-directory guard, not a write fence. Options, in order of strength: turn on the runtime sandbox with `readwritePaths` = write roots and `readonlyPaths` = reference roots; ask or deny any non-read-only shell command that names an absolute or climbing path outside the write roots; or treat the parser as advisory and rely on the permission handler's `shell` request (whose `possiblePaths` was empty here, so not that).
2. **Persistent shell working directory.** The hook's `workingDirectory` is the session's, not the shell's. The `bash` tool keeps one shell per session, so `cd <repoB>` in one call followed by `echo x > f` in the next would be judged against A. R-07 treats the `cd` itself as outside and asks or denies it, which covers this only as long as no `cd` outside the write roots is ever allowed. Not exercised live.
3. **Tool catalog.** `core/src/agents/tool-catalog.ts` lists `create` and `edit` as the write tools. The runtime offered `apply_patch` with a string argument. Mapping calls to policy targets (R-07's open item) must parse patch headers, and must treat an unknown tool that may write as a write, not as `other`. S-02 owns the tool list.
4. **Reference roots are not passed to the runtime.** `SessionService` sets `workingDirectory` to the first write root and never passes `additionalDirectories`. Native reads of reference roots still work through the permission handler, but each `view` then costs two requests, not one. The adapter should pass reference roots as `additionalDirectories` (and re-supply them on resume, as the SDK requires), and the permission handler should approve `read` only inside write and reference roots, using `resolvedPath` or R-07's `realPath` for symlinks.
5. **Hook `allow` may skip the runtime's request.** `bridgeHooks` returns `permissionDecision: "allow"` for every allowed call. In the first `read` run, with the hook returning `allow`, no `read` request fired. That run also had fixtures in `$TMPDIR`, so the cause was not isolated. If `allow` does pre-approve, Pica's policy is the only gate for reads. That is consistent with the design, but the read gate and the outside-roots rule must then cover every read tool (`view`, `grep`, `glob`, and shell reads).
6. **R-08's repo tools are not needed for access.** The A6 fallback ("cross-repo access only through engine tools") is not required. `repo_read`/`repo_search`/`repo_list` keep their purpose: they work on uncloned workspace repos, and they let the `repo-scout` agent search other repos at worker-tier cost. Their open item stands: they are not mapped to policy targets, so read exclusions and the read gate do not apply to them yet.

## Reproduce

```sh
PICA_LIVE=1 make verify UNIT=S-04   # three live checks (6 prompts) and the offline A6 check
node --experimental-strip-types --disable-warning=ExperimentalWarning spikes/s-04-multi-root/s04.mjs read|write|concurrent|guard
```

The live checks need a Copilot CLI login (`copilot login`). Without `PICA_LIVE=1` they are skipped, and they never run in CI.
